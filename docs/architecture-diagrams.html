Filter Pipeline Detail

applyFilter() — DiscoverViewModel.swift

Four-stage filter pipeline applied to distance-sorted venues:

  1. VenueFilterState.apply() — selectedCategory? → filter by category match; selectedBusynessLevel? → filter by level match
  2. openNowOnly? → filter venue.isOpen == true
  3. ratingFilter? → filter venue.rating >= threshold (3.5, 4.0, or 4.5)
  4. priceFilter? → filter by price bucket:
    • $ → FREE or INEXPENSIVE
    • $$ → MODERATE
    • $$$+ → EXPENSIVE or VERY_EXPENSIVE

Output splits:

  • popularVenues: base + busyness ≥ 4, sorted desc, max 10
  • sweetSpotVenues: base + busyness 1-3, max 8
  • filteredVenues: base (sorted by rating if ratingFilter active)

Venue ID Generation

Critical: Venue ID Format venue.id = normalized_name + "_" + lat(5 decimals) + "_" + lng(5 decimals)
Example: "the-coffee-shop_43.65107_-79.34729"

This ID is used everywhere: fusion cache keys, saved venue lookups, deduplication across MapKit searches. 5 decimal places = ~1.1m precision. Do not change the format.

6. Critical: Do Not Modify

These areas have subtle, load-bearing logic. Changing them without full understanding risks breaking core functionality.

1. Venue ID Generation

Models/Venue.swift

Normalized name + 5-decimal lat/lng. Used as cache key, saved venue key, dedup key. Changing format breaks all lookups.

2. MapKit Rate Limiting

VenueSearchService.swift

35 req/60s limit with 15 reserved for Apple internal calls. Relaxing this causes silent search failures from Apple's server.

3. Phase A/B Search Pipeline

MapViewModel.searchVenues()

Phase A pre-populates cache for instant pin colors. Phase B fills gaps with progressive refreshes. Removing any phase causes grey flash or stale data.

4. Clustering Debounce

MapViewModel.recomputeClusters()

100ms debounce during progressive loading. Without it, map stutters as 12 concurrent search batches complete.

5. Busyness Carry-Over Priority

applyAllBusynessData()

Order: carry-over > cached > offline. Priority 1 prevents pins from flashing grey between searches. Order matters.

6. FusionService Cache Invalidation

FusionService.swift

500m movement, TTL, and explicit refresh triggers. LRU eviction at 500 entries. Hours transition refresh keeps open/close accurate.

7. Auth Venue Restore Token

AuthState.swift

pendingVenue + pendingVenueTab + venueRestoreToken flow. Without it, users lose their place when prompted to sign in mid-action.

8. Task Cancellation in deinit

MapViewModel.deinit

7 async tasks cancelled: searchTask, refreshTimer, hoursTransitionTask, clusterDebounceTask, expandTask, prefetchTask, followUpTask. Missing any causes retain cycles.

7. Improvement Opportunities

Architecture

  • DiscoverViewModel duplication: Re-implements filter logic overlapping with VenueFilterState. Could consolidate into a single reactive pipeline.
  • 6 environment objects: Consider a single AppState container or @Observable macro (iOS 17+).
  • Service singletons: FusionService.shared makes testing harder. Could use protocol-based injection.

Performance

  • Clustering on main thread: O(n) for 300 venues is fast, but could move to a background actor for safety.
  • Distance sorting: Full sort on every update. Could use a spatial index for O(log n) queries.
  • Adaptive batch count: Currently 12 MapKit searches always. Could stop early if 200+ venues found.

User Experience

  • No pull-to-refresh on Discover: Users must switch tabs or wait for live refresh.
  • No offline mode: Could cache last-known state to UserDefaults.
  • No visible search bar on Map: searchText exists but isn't surfaced in the UI.

Code Quality

  • Magic numbers: 0.005 threshold, 300ms debounce, 800m camera — should move to AppConstants.
  • Error handling: Catch blocks mostly log. No user-facing error states ("No internet").
